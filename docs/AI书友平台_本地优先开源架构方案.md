# BookMate 本地优先开源架构方案

> 版本：v1.0  
> 日期：2026-08-17  
> 新定位：任何人都能用自己的书、感受与边界，构建一位可以长期把阅读谈深的私人 AI 书友；模型、知识库和查询能力都只为这段交流服务。

## 0. 产品根本：先有书友关系，再有技术方案

BookMate 要解决的并不是“怎样更快处理一本书”，而是“读完以后，怎样继续和一位能接住问题的书友谈下去”。书单、摘要、问答和价格信息并不稀缺；稀缺的是能理解一段阅读为何触动你、愿意把一个问题留在桌上慢慢谈的人。

因此，BookMate 的首要承诺是一个**私有、可持续、边界由读者掌握的 AI 书友空间**：读者可以用自己的书、摘录、感想、问题与确认过的记忆，逐渐形成下一次交流所需的共同语言。这里的“更懂得继续交流”来自明确保存和可追溯的线索，不是模拟真人关系，也不是声称模型拥有未被提供的人生经验。

产品优先级必须始终是：

1. **对话的共振与深度**：先帮助读者把一个真实的问题谈下去，而非生成一页结论；
2. **私有书房与图书馆**：让书、版本、阅读痕迹与剧透边界成为长期交流的可靠上下文；
3. **透明与可控**：读者决定哪些线索被记住、哪些资料参与当轮对话、何时使用远程模型；
4. **技术与外部能力**：RAG、图书馆查询、价格查询、搜索和 Agent Skills 都是证据与信息的补充，不能主导首页、打断阅读关系或暗中扩展数据范围。

## 1. 从技术堆栈回到书友关系

前一版“托管网页 + 开源 Agent Kit”适合商业产品，但不足以成为容易传播的开源项目。对开源版更重要的检验是：

> 不注册 BookMate 账户、不连接官方服务器、不购买商业数据，一个普通用户能否在自己的电脑上完成安装、选择模型、上传一本书并开始长期交流？

答案必须是“可以”。因此建议将开源版提升为主产品形态之一：

- **BookMate Local**：完整本地产品、本地优先、网页操作、单机数据所有权。
- **BookMate Agent Kit**：Skills、MCP、协议和连接器，服务高级用户与其他 Agent 宿主。
- **BookMate Cloud（未来可选）**：免安装、同步、托管模型和商业数据连接器。

开源版不是云端版的残缺客户端。它应当独立完成模型聊天、本地知识库、记忆、双模式书友和数据导入导出。

## 2. 用户实际需要的不是“部署一套 AI 基础设施”

个人用户通常不愿意处理：

- PostgreSQL、Redis、Elasticsearch、对象存储和向量数据库；
- 多个容器、反向代理、跨域和端口配置；
- embedding 模型、reranker、chunk 参数和索引任务；
- MCP、RAG、token、temperature 等术语；
- API Key 写在哪个配置文件。

用户只想完成四件事：

1. 打开 `http://localhost:8000`。
2. 选择一个模型服务并测试连接。
3. 上传自己的 EPUB、PDF、TXT 或 Markdown。
4. 选择一本书，开始和同一位书友聊天。

所以“简单”必须体现在默认架构，而不是仅在 README 写一条很长的安装命令。

## 3. 设计原则

### 3.1 零外部基础设施默认值

默认只使用：

- 一个 BookMate 进程/容器；
- 一个网页端口；
- 一个本地数据目录；
- 一个 SQLite 文件；
- 用户选择的模型接口。

PostgreSQL、Redis、Qdrant、Milvus、MinIO 等全部是规模化可选项，不进入个人版默认部署。

### 3.2 Local-first，而非 Local-only

- 文档、索引、对话和记忆默认保存在本机。
- 模型可以是本机服务，也可以是用户选择的远程 API。
- 联网搜索、价格和馆藏默认关闭，按 Skill 单独启用。
- 未来云端同步必须是用户显式选择，不能成为本地版依赖。

### 3.3 先可用，再增强

本地检索分级：

| 级别 | 默认 | 依赖 | 用途 |
|---|---:|---|---|
| L0 模型知识 | 是 | 聊天模型 | 经典书思想交流，不承诺具体版本引文 |
| L1 本地关键词/字符检索 | 是 | SQLite | 零配置定位用户文档片段 |
| L2 Embedding 检索 | 否 | embedding 接口 | 同义表达、跨语言和概念召回 |
| L3 Reranker | 否 | rerank 模型 | 大知识库提高精度 |

不能强迫用户先配置 embedding 才能上传第一本书。个人书库规模小时，简单检索加长上下文已经足够验证核心体验。

### 3.4 模型供应商中立

内部定义统一 `ModelGateway`，不让业务代码直接依赖某个 SDK。首版支持两种 HTTP 适配器：

- `chat_completions`：调用用户指定 Base URL 下的 `/chat/completions`，面向提供 OpenAI Chat Completions 风格接口的服务。
- `responses`：调用 `/responses`，面向支持 OpenAI Responses API 请求形态的服务。

“OpenAI-compatible”不是一个由 OpenAI 为第三方实现认证的完整协议标准。不同服务对流式输出、JSON Schema、工具调用、图像、usage 和错误结构的支持并不一致。因此首版只使用最小公共子集：模型名、文本消息/输入、非流式文本输出，并在 UI 中提供连接测试。

OpenAI Docs 在当前开发网络返回 HTTP 403；发布前必须在可访问环境重新核对当时的 Responses 与 Chat Completions 官方字段。第三方兼容性以 BookMate 的实际探测结果为准，不能仅依据厂商宣传。

## 4. 推荐部署形态

### 4.1 首选：单容器

```text
docker run / docker compose
  -> FastAPI API
  -> FastAPI 托管 Next.js 静态页面
  -> SQLite + 上传文件目录
  -> 用户模型 HTTP API
```

只有一个对外端口 `8000`，浏览器与 API 同源，不需要 CORS，也不需要长期运行 Node.js。

数据卷：

```text
./bookmate-data:/data
```

删除容器不会删除个人书库；备份整个目录即可迁移。

### 4.2 无 Docker：本地开发/高级用户

提供 PowerShell 和 shell 启动脚本：

1. 自动创建 Python venv；
2. 安装 API；
3. 如果缺少静态网页，提示构建或使用开发服务器；
4. 启动浏览器可访问的单一地址。

未来可以用 PyInstaller/Tauri 打包桌面版，但不应在验证产品前引入桌面打包复杂度。

### 4.3 可选扩展部署

当用户达到多人或大规模书库后，可以替换：

- SQLite -> PostgreSQL；
- 本地文件 -> S3 兼容对象存储；
- 本地检索 -> pgvector/Qdrant；
- 单进程任务 -> Redis 队列。

领域契约保持不变，个人版不承担这些组件的维护成本。

## 5. 单机逻辑架构

```text
浏览器 Web UI
  -> Companion API
     -> Role & Flow Orchestrator
     -> ModelGateway
        -> chat_completions adapter
        -> responses adapter
     -> ContextBuilder
        -> 当前会话
        -> 全局书友记忆
        -> 当前书籍记忆
        -> 本地文档片段
     -> LocalStore
        -> SQLite
        -> uploads/
     -> Optional Skills
        -> library / price / web search
```

所有模型调用前先生成一份可审计上下文包：

```json
{
  "mode": "book_room",
  "active_book_id": "...",
  "memory_ids": ["..."],
  "document_chunks": ["..."],
  "search_policy": "off",
  "external_tools": []
}
```

这让“模型用了什么依据”可被 UI 展示，也方便更换模型时复现问题。

## 6. 数据目录

```text
bookmate-data/
├─ bookmate.db                 # 设置、文档、分块、会话、记忆
├─ uploads/                    # 用户原始文件，名称使用内部 ID
├─ exports/                    # 用户主动导出的数据
├─ logs/                       # 默认不记录完整私人对话
└─ models/                     # 可选本地 tokenizer/embedding 资源
```

SQLite 表建议：

| 表 | 责任 |
|---|---|
| `settings` | 模型、检索、搜索与界面设置 |
| `knowledge_bases` | 知识库，例如“我的文学书架” |
| `documents` | 文件元数据、解析状态、哈希和版本 |
| `chunks` | 文本块、定位信息和可选向量 |
| `works/editions` | 用户文件与书目版本关联 |
| `conversations/messages` | 对话和消息 |
| `memories` | 全局、单书和会话记忆 |
| `citations` | 回答与本地片段/外部来源的关系 |

首个实现可以只有默认知识库，不需要用户先理解“库”的概念；数据模型保留 `knowledge_base_id`，以后再开放多个知识库。

## 7. 本地知识库流程

### 7.1 上传

1. 检查扩展名、大小和 ZIP/EPUB 解压安全。
2. 计算 SHA-256，避免重复导入。
3. 原文件保存在 `uploads/{document_id}`。
4. PDF 提取页文本；EPUB 按 spine 顺序读取 XHTML；TXT/Markdown 直接解析。
5. 文本规范化并按段落/章节分块。
6. 保存来源定位：页、章节、文件和 chunk ordinal。
7. 默认建立零配置本地索引。
8. 若配置 embedding，再异步补充向量；失败不影响关键词检索。

### 7.2 检索

不是每轮聊天都检索。只在以下场景调用：

- 用户要求精确原句或版本依据；
- 问题明确与当前上传书相关；
- 模型承认不确定；
- 用户打开“优先依据我的资料”。

首版检索适合个人书库：按文档范围筛选、字符/词语相关度召回，再把 3～6 个片段放入上下文。以后可以无缝增加 embedding 和 rerank。

### 7.3 管理

普通用户界面只需要：

- 文件名、类型、大小、状态、导入时间；
- 选择为当前书；
- 重新解析；
- 删除文件及索引；
- 导出元数据；
- 明确显示“文件仅存本机”或当前模型是否会把片段发送到远程服务。

最后一点非常重要：文件本地保存不代表内容永不离开电脑。如果用户配置远程模型，检索到的片段会随 prompt 发给该模型服务，UI 必须说明。

## 8. 模型配置

最小设置：

| 字段 | 示例含义 |
|---|---|
| `protocol` | `chat_completions` 或 `responses` |
| `base_url` | 用户的 API 根地址，通常包含 `/v1` |
| `model` | 服务端识别的模型 ID |
| `api_key` | 可选；仅保存在本地数据目录或由环境变量提供 |
| `timeout_seconds` | 默认 60 |

当前实现还支持多个本地 `model_profiles` 配置档。每个配置档独立保存名称、协议、Base URL、模型 ID、可选 API Key 与超时；`model.default_profile_id` 记录新对话的默认档。聊天请求可以携带一个配置档 ID，只影响该轮模型调用，不改变书房、剧透边界或读者笔记作用域。API Key 只保存在本地，任何读取配置档的 API 响应都只返回是否已配置。模型连接与 `reader.display_name` 等界面偏好必须和书架、资料、阅读痕迹分开展示；后者只影响本地界面，不能自动成为长期记忆或被送往模型服务。
| `temperature` | 默认低到中等，用户无需首屏看到 |

环境变量覆盖本地设置，便于 Docker 与自动部署：

```text
BOOKMATE_MODEL_PROTOCOL
BOOKMATE_MODEL_BASE_URL
BOOKMATE_MODEL_NAME
BOOKMATE_MODEL_API_KEY
```

配置测试必须实际发送一条最小请求并返回：

- 连接成功/失败；
- HTTP 状态和可读错误；
- 是否解析出文本；
- 耗时；
- 不回显 API Key。

不要在首版自动探测局域网模型服务或扫描端口，这会增加隐私和安全疑虑。

## 9. 上下文构建与成本

推荐预算顺序：

1. 稳定书友 Role 与安全边界；
2. 当前用户消息和最近对话；
3. 当前书共同线索；
4. 用户确认的少量长期记忆；
5. 本地检索片段；
6. 外部搜索结果。

不要把整本书每轮发送给模型。短书可以在模型支持时利用长上下文和缓存；普通情况仍应发送少量相关片段。需要精确引用时，回答必须指向上传文件中的页/章节/chunk，不能让模型自行编造页码。

## 10. 隐私与安全默认值

- 服务默认只监听 `127.0.0.1`；Docker 映射到本机端口，不默认暴露公网。
- 不提供默认账户系统，因为这是单用户本地应用；一旦公网部署必须增加认证。
- API Key 在接口响应中永远只返回 `configured: true/false`。
- 上传文件名不直接作为磁盘路径，防止路径穿越。
- EPUB 解压限制条目数量、单条大小和总展开大小，防止 ZIP bomb。
- PDF/EPUB 解析失败要隔离到单文档，不影响服务启动。
- 默认日志不包含完整对话、文档正文和 API Key。
- 删除文档时同时删除文件、chunks、向量和引用关系。
- 提供一键导出和一键清空，但清空必须二次确认。

## 11. 开源仓库结构

```text
bookmate-local/
├─ apps/web/                   # 本地管理和书友界面
├─ services/api/
│  ├─ app/model_gateway.py
│  ├─ app/knowledge.py
│  ├─ app/storage.py
│  └─ app/companion.py
├─ packages/agent-kit/
│  ├─ skills/                  # 可移植的 Skill 与 provider 契约
│  └─ README.md
├─ docs/                       # 产品、架构与数据边界
├─ data/                       # gitignore，仅保留占位文件
├─ Dockerfile
├─ docker-compose.yml
└─ README.md
```

Web UI 调用本地 API；MCP Server 后续调用相同领域服务，而不是复制一套存储和检索逻辑。

## 12. 开源传播为什么会更好

这个定向让项目有五个清晰传播点：

1. **数据属于自己**：书、对话和记忆都能留在电脑上。
2. **模型由自己选择**：本地或远程、便宜或强大都可替换。
3. **五分钟有结果**：一个容器、一个端口、一个目录。
4. **不是通用知识库换皮**：核心是稳定书友、单书记忆和思想心流。
5. **能力可以带走**：同一份 Skill/MCP/数据可以被其他 Agent 使用。

但也必须诚实：如果只做“OpenAI 兼容聊天 + 上传 PDF”，它会淹没在大量本地知识库项目中。BookMate 必须继续把差异化投入在书友 Role、关系记忆、对话评测、书籍作用域和推荐，而不是追逐更多向量数据库选项。

## 13. 分阶段实现

### M0：本地闭环

- 单容器单端口；
- SQLite 与本地数据卷；
- 模型配置、连接测试；
- TXT/MD/PDF/EPUB 上传、列表、删除；
- 零配置检索；
- 双模式聊天读取本地片段；
- 导入数据不连接 BookMate 官方服务。

### M1：真正的个人书友（当前已完成基础版）

- 已完成：对话持久化；全局/单书/会话记忆；用户确认记忆候选；当前书绑定上传文档；本地 JSON 导出。
- 待完成：记忆编辑、合并、冲突解释；恢复导入；更精细的页/章节引用体验。

### M2：可选增强

- OpenAI-compatible embedding adapter；
- 混合检索和 reranker；
- MCP Server；
- 图书馆、价格和搜索 Skills；
- 多知识库和插件管理。

### M3：易安装发行

- Windows/macOS/Linux 安装包；
- 自动升级与数据迁移；
- 可选局域网访问与认证；
- 可选云同步，但本地模式继续独立可用。

## 14. 最终架构判断

推荐现在就把开源项目的技术承诺改为：

> BookMate 是一个本地优先、模型可替换、数据可迁移的个人 AI 书友。默认不需要云端账户、向量数据库或商业书库；用户可以直接用模型已有知识交流，也可以上传自己合法拥有的书，让书友基于具体版本继续长期对话。

这比“建设全球书籍 RAG 平台”更现实，也比“只发布两个 Skills”更有独立价值。全球书目、馆藏和价格仍然重要，但它们降级为可选连接器；本地书友本身必须在完全没有这些连接器时依然成立。
